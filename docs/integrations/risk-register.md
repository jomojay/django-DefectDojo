# Risk Register — SSO, Epic 0 (RBAC), and SolarWinds Integrations

**Scope:** the consolidated risk register (§9 of the delivery plan) for all three initiatives covered by [`INTEGRATIONS_ROADMAP.md`](../../INTEGRATIONS_ROADMAP.md) — SSO (Epic 1), RBAC reactivation (Epic 0), and the SolarWinds Service Desk integration (Epic 2/3). This file is **not owned by any one epic** — it's referenced by risk ID (`R1`, `R9`, `R28`, etc.) from all three epic files and from the master roadmap. Read the master file first for the big picture and the Documentation Map explaining how everything here fits together.

**Convention used throughout this file:** section references like "§7" or "§8.3" point to subsections of the epic files this risk register is filed against — §5/§6 are in [`epic1-sso.md`](epic1-sso.md), §7 is in [`epic0-rbac-reactivation.md`](epic0-rbac-reactivation.md), §8 is in [`epic2-3-solarwinds.md`](epic2-3-solarwinds.md), and §9/§10/§11 refer to this document, the master roadmap's Rollout Plan, and [`task-list.md`](task-list.md) respectively. "§3" refers to the master roadmap's Finalized Decisions section (where the named assumptions A1-A3 live).

## 9. Risk Register

| ID | Risk | Mitigation |

| R1 | ~~OS authorization is binary per product, no Reader/Writer/Owner granularity~~ | **Closed 2026-08-11** by Epic 0 (§7, in `epic0-rbac-reactivation.md`), all seven PRs landed. | R2 | Middleware ordering — `SocialAuthExceptionMiddleware` misplaced causes redirect loops | Insert after `AuthenticationMiddleware`, before `LoginRequiredMiddleware` |

| R6 | SolarWinds token rotation breaks sync silently | Dedicated service account + health-check task + runbook |

| R9 | `finding.severity` → SolarWinds priority mapping is tenant-specific, **and the API silently no-ops on an invalid priority label instead of erroring** (confirmed live 2026-09-18, §8.1/§8.3, in `epic2-3-solarwinds.md`) | Captured in `severity_priority_map` at config time as labels, never assumed; client validates the outgoing label against that map before every write since the API won't catch a bad one |
| R10 | Upstream DefectDojo drift — restored SSO code diverges from a future upstream re-add | Review periodically against upstream tags; this is intentionally isolated in `social_pipeline.py`/settings, not scattered |
| R11 | Repeating JIRA's plaintext-credential anti-pattern for SolarWinds | Code-review gate requiring `dojo_crypto_encrypt` usage |
| R19 | Same silent-no-op risk as R9 applies if `severity_priority_map` goes stale after a tenant renames/removes a priority label (no ID to detect drift, only a label string) | Health-check task should periodically verify a test write's priority actually changed, or watch for incidents whose priority silently didn't update — extends R6's health-check task |
| R20 | **The `Updated_at` filter has no arbitrary-timestamp granularity** (found 2026-09-18 while building `client.py`, reading the spec's `/incidents` GET parameters). It accepts only a fixed day bucket (`updated=1\|7\|14\|30\|60\|90`) or an explicit **day-granular** range (`updated=Select Date Range` + `updated_custom_gte`/`lte`, format `Mar 2 2023`). A 10-minute poll (§8.6) therefore cannot ask for "changed in the last 10 minutes" — the tightest possible window is a full day, so every run re-fetches the same day's incidents repeatedly. This is a correctness constraint, not just a cost one: the reconciliation cannot infer "this changed since last poll" from the fact that the API returned it | `list_incidents_updated_since()` snaps a caller's `datetime` up to the smallest covering bucket (falling back to a date range past 90 days), so the result is always a **superset** of the requested window, never a subset. Epic 3's reconciliation must therefore (a) be fully idempotent — re-processing an already-mitigated finding must be a no-op — and (b) compare each incident's own `updated_at`/state against the `last_synced_state` cursor rather than trusting that a returned incident actually changed. Also the reason for the page cap and the R7 batching rule: a day-wide window on a busy tenant is a lot of pages |
| R21 | ~~**Round-tripping `api_token` through a plain `ModelForm`/serializer double-encrypts it.** The field stores ciphertext, so a form that renders the current value and saves it back runs `dojo_crypto_encrypt` over an already-encrypted string; the credential then decrypts to garbage and every API call 401s, looking exactly like the token rotation of R6.~~ | **Closed 2026-09-18** by the config UI/API pass, structurally rather than by convention. The form **excludes `api_token` from `Meta.fields`** and declares it as a plain form field, so `construct_instance()` has no path to the column at all; `set_api_token()` runs only when the admin typed something. The serializer declares it `write_only` and writes it only through `set_api_token()` (a plain `ModelSerializer` would have stored plaintext — R11). Both halves tested: ciphertext byte-identical across two saves without retyping (with a control test proving the nonce makes that assertion meaningful), and no response body from either layer contains the token in plaintext **or** ciphertext. The correct JIRA citation is `dojo/jira/forms.py:79-87`, not `86-93`. |
| R22 | **A configuration with an empty `severity_priority_map` and `push_enabled=True` can never push anything, and nothing said so until the first finding.** Found 2026-09-18 while building the config form. `client._validate_priority()` deliberately hard-fails on an empty map (there is nothing to validate an outgoing label against, and the API accepts an invalid priority with a 200 — R9/R19), so every push raises `SolarWindsConfigurationError` at run time. The previous `clean()` happily accepted the combination, since "no unknown severity keys" is trivially true of `{}`. | `SolarWinds_Instance.clean()` now rejects `push_enabled` with an empty map, which covers the form, the REST serializer (it calls `clean()`) and the Django admin in one place. The serializer passes the *stored* `push_enabled` into that check so a PATCH flipping only that flag is still validated. **Residual:** a direct `.save()` from code or a fixture bypasses `clean()` entirely, as with every other model-level rule in this codebase — Epic 3's push hook should treat `SolarWindsConfigurationError` as "this instance is misconfigured, alert", not as a retryable failure. |
| R23 | **The per-product mapping routes are gated on system-level configuration permissions, not on the mapped Product's own permissions.** Consequence, accepted deliberately: a Product Owner cannot set up their own product's ticket routing, and anyone holding `dojo.change_solarwinds_product` can route *any* product's findings to any site/department/assignment group. | Deliberate for this pass: the mapping decides which external tenant and queue a product's findings land in, alongside a shared service-account credential — that is integration configuration, and it matches how `tool_config` treats the same kind of value. The alternative (object-level `("object", Product, "edit", "pid")`) would need the mapping routes rekeyed on `pid` and a `SolarWinds_Product` branch added to `authorization.user_has_permission()`, which currently raises `NoAuthorizationImplementedError` for unknown models. Revisit if per-product self-service is ever asked for; until then the delegated-configuration story is "a config admin owns the mappings". |
| R24 | ~~**`SolarWinds_Ticket` had no instance reference, so the inbound poll could only join incidents to tickets by `incident_id` alone.** Found 2026-09-18 while building the poll. Incident ids are unique *within* a tenant, not globally, and `SolarWinds_Instance` is explicitly a multi-row model (unique `configuration_name`, a list UI, per-product mappings that can point at different tenants). Two configured tenants reusing the same numeric id — entirely normal, both start counting from the same place — would make one tenant's resolved incident mitigate the *other* tenant's finding. Silent data corruption, with no error anywhere.~~ | **Closed 2026-09-18** by migration `0280`, which adds `SolarWinds_Ticket.solarwinds_instance` (FK, `CASCADE`, nullable purely so the migration is additive). The outbound hook sets it on every row it writes, and `reconcile_resolved_incidents()` filters on it before the `incident_id` join, so the query can only ever see one tenant's tickets. Additive and safe to apply ahead of the code: Epic 3 is the first code in this fork that ever *creates* a `SolarWinds_Ticket`, so no deployment has rows to backfill. Tested with two instances where the second tenant returns an incident whose id matches the first tenant's ticket; the first tenant's finding is untouched and no cursor moves. `CASCADE` is deliberate — an orphaned link row could never be reconciled anyway, since the credentials needed to poll it went with the instance. |
| R25 | **A concurrent double-save of the same finding can create two incidents for it.** `push_finding_internal()` checks "does this finding already have a ticket?" and then makes an HTTP call before writing the link row, so two workers racing on the same finding can both pass the check. The `OneToOne` on `SolarWinds_Ticket.finding` prevents the second *row*, but only after the second *incident* already exists in the tenant. Narrow — it needs two saves of one finding overlapping within the duration of one API call — but the consequence is a ticket nobody will ever close. Not fixed by holding a row lock across the check: that would mean an open `SELECT … FOR UPDATE` for the length of a network round trip. | Mitigated to "loud, not silent": the link row is written with `get_or_create`, and losing the race raises a `solarwinds_update` notification naming **both** incident ids and saying explicitly which one is orphaned, so an operator can close it. Accepted for this pass. A real fix is a claim-row-first protocol (insert the link row with a blank `incident_id` inside a transaction, call the API, then fill it in, deleting the claim on failure), which trades this race for a stale-claim problem — a worker that dies between claim and fill-in blocks that finding's push permanently until something reaps blank-id rows. Revisit if duplicate incidents are ever actually observed. |
| R26 | ~~**Only the config-driven half of the outbound trigger is reachable; the explicit per-finding push has no caller.** `push_all_findings` worked from every save path, but `push_to_solarwinds` was threaded through `Finding.save()`/`post_process_finding_save` with nothing in the UI or the REST API setting it. Two consequences: an operator's only choice was all-mapped-severity-findings-or-nothing per product, and the threaded parameter was untested in production use (unit tests only).~~ | **Closed 2026-09-19 for the screens where a human decides; see the scope line below.** A `push_to_solarwinds` checkbox is wired into **Add Finding** (`dojo/test/ui/views.py`), **Edit Finding** (`dojo/finding/ui/views.py`) and **both template trees**, plus a write-only `push_to_solarwinds` field on `FindingSerializer`/`FindingCreateSerializer`. Computed at the call sites as the **checkbox alone**, not `is_push_all_findings_auto(...) or <checkbox>` as R26 originally proposed and as JIRA does it — the config-driven half is resolved inside the post-save hook here, so OR-ing it in would be a no-op implying a mechanism that is not there; the auto state instead reaches the form as `push_all` and renders the box checked and disabled, which is what JIRA's operator actually sees. The checkbox is only rendered when it can do something (`helper.is_manual_push_available`), and is disabled with the incident named when one already exists, because there is no outbound update path. **Explicitly still open, and deliberately:** bulk edit and add-finding-from-template are not wired — bulk edit is the most dangerous place to put this control (one careless multi-select is the flood R32 exists to prevent) and wants a confirmation step and a count of its own. **The `verified` gate question R26 raised is answered, not deferred:** it stays absent. Volume control is now `auto_push_severities` (R32), which is a per-deployment configuration an operator can see on one screen, rather than a second gate sourced from system settings that would make "why did this finding not create a ticket?" a two-place question. An unverified finding on an auto-push severity still opens a ticket. |
| R27 | **The outbound hook costs one SQL query on every `Finding.save()` in every deployment, including the ones that never configure SolarWinds.** Direct consequence of resolving `push_all_findings` inside the post-save hook instead of at the call sites (R26): something has to ask "is this integration configured?" on each save. Found 2026-09-18 when the change broke **26 pinned query-count subtests** across `unittests/test_tag_inheritance_perf.py` and `unittests/test_importers_performance.py`, every one of them by exactly +1 per save. Those files exist as tripwires for precisely this, so the failure was the system working. | `helper.any_push_mapping_exists()` is deliberately the *cheapest possible* form of the question — one `EXISTS` against `SolarWinds_Product` (a table holding single digits of rows in practice) — and it runs **before** `get_product()`, which would otherwise walk `test -> engagement -> product` for three queries on a finding the single-save path loads without `select_related`. So the real choice was +1 or +4, not +1 or +0. Cost profile measured, not assumed: scan import and reimport pay **+1 per import** regardless of finding count, because `post_process_findings_batch` answers the question once per batch (the 19-finding ZAP baselines moved by 1, not 19); only findings created or edited one at a time pay +1 each. The 26 baselines were updated with an inline comment at each site explaining the move, so a future reader sees an accepted cost rather than an unexplained number. **Rejected alternative:** memoising the answer in-process with signal invalidation. It would make the first save in a process cost 1 query and the rest 0, which turns every pinned baseline order-dependent and therefore flaky — strictly worse for a suite whose whole purpose is deterministic tripwires — and it would go stale across processes (a config change in the web worker would not reach the Celery worker). Revisit only if a profile ever shows this query mattering; the fix would be to close R26 instead, which removes the need for the check entirely. **Amended 2026-09-19** by R28: the cost profile above still holds exactly (+1 per single save, +1 per import batch), but it now depends on importer call sites passing `defer_post_processing=True` rather than on those saves happening to skip post-processing altogether. |

| R29 | ~~**A network blip permanently failed a ticket push, with zero retries.** `client._request()`'s retry loop only re-looped on `RETRYABLE_STATUS_CODES` (429/502/503/504), which are checked *after* a response comes back. `except requests.RequestException: raise SolarWindsAPIError(...)` re-raised immediately, escaping the `for attempt in range(...)` loop on the first connection reset, read timeout or DNS failure — i.e. the single most ordinary transient failure got no retry while a 503 from the same tenant got four. `helper.TRANSIENT_ERRORS` did not include `SolarWindsAPIError` either, so the Celery layer did not catch it back either.~~ | **Closed 2026-09-19.** Transport failures now take the same retry path as a 429: `_sleep_seconds(attempt, None)` was already written to accept a missing response (no `Retry-After` to honour, falls through to jittered exponential backoff — verified, not assumed), and `SolarWindsAPIError` is raised only once `max_retries` is exhausted, matching the 429/5xx branch exactly. **4xx deliberately still not retried** — deterministic, and retrying a malformed payload just burns rate-limit budget (R7) for the same answer; pinned by `test_a_client_error_is_still_not_retried`. **Residual, and the reason `TRANSIENT_ERRORS` was left alone:** a `POST /incidents` that fails at transport level may already have created the incident — the response was lost, not the request. So a retry can create a duplicate that no link row points at: R25's orphan shape, reached by a different route. That hazard already existed for the 502/503/504 retries and is bounded to the client's in-request budget; adding transport errors to the Celery-layer `TRANSIENT_ERRORS` would spread the same window across a 10-minute countdown and up to three more attempts, which is a materially worse trade for a failure the in-request budget usually absorbs. Revisit together with R25 if duplicate incidents are ever actually observed; the real fix for both is the claim-row-first protocol described there. |
| R30 | ~~**A reopened ticket left its finding closed forever.** `_reconcile_one()` only acted on the not-resolved → resolved transition.
